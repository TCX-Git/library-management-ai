# 项目宪法（Constitution）

> 本文件是图书管理系统项目的最高约束规范，约束所有 Agent（需求分析、UML 建模、架构设计、编码、测试）的行为。
> 所有 specs、UML、代码、测试的生成与修改必须遵守本宪法。
> 依据：`specs/00-project-brief.md`（需求背景）与 `specs/01-clarifying-questions.md`（澄清问题）。

## 1. 目的与适用范围

本宪法面向本项目（图书管理系统）的全部 Agent 辅助生成活动，包括但不限于：

- 需求规格（Specs）与设计文档
- UML 建模（用例图、类图、时序图、活动图等）
- 数据库设计
- 源代码
- 自动化测试

凡本宪法与具体任务说明冲突时，以本宪法为准；确需偏离的，须先经人工审查批准并记录理由。

## 2. 核心原则（总纲）

1. **Spec 驱动开发**：先有规格，后有实现。任何代码与测试必须可追溯到已定稿（baseline）的 Spec。
2. **UML-as-Spec**：分析与设计以 UML 图为核心表达载体，图形即规格，文字描述只作补充。
3. **人工审查优先**：Agent 生成的任何内容（规格、UML、设计、代码、测试）在采纳前必须经过人工审查。
4. **架构先行**：遵循分层架构与 MVC 模式，架构边界在编码前以 UML/文档形式确定。

## 3. Agent 行为约束

1. Agent 只允许在其被授权的范围内产出内容，不得越权修改授权范围之外的文件或产物。
2. Agent 生成内容时必须显式标注"本内容由 Agent 生成，未经人工审查，不得直接作为实现依据"。
3. Agent 不得擅自删除、覆盖或重写已 baseline 的 Spec、UML 与设计文档。
4. Agent 修改代码前，必须确认对应 Spec 已 baseline 且变更点已在 Spec 中体现；否则先更新 Spec 并经人工确认。
5. Agent 不得引入超出项目范围的技术、框架或第三方依赖；确需引入的，须在 Spec 中说明并经人工批准。

## 4. Specs 规范与 Baseline 管理

1. 需求规格采用结构化、可追溯的形式表达（如 EARS 格式），每条需求应可定位、可验证。
2. **Baseline 定义**：一份 Spec 经人工审查确认后即进入 baseline 状态，成为后续设计、编码、测试的唯一事实来源。
3. **Baseline 冻结原则**：baseline 后的 Spec 不得擅自修改。任何变更必须走变更流程——提出变更、说明理由与影响范围、人工审查、重新定稿。
4. 禁止 Agent 以"顺手优化""补充细节"为由静默修改 baseline 文档。

## 5. UML-as-Spec 规范

1. 所有 UML 图必须采用**文本格式**编写，仅允许使用 **PlantUML** 或 **Mermaid** 语法。
2. 禁止使用截图、图片或不可文本化编辑的图形作为规格载体。
3. UML 图必须保存在源码仓库中，随规格一并版本化管理，保证可评审、可 diff、可追溯。
4. 关键 UML 图（用例图、领域类图、关键用例时序图）在编码前必须定稿并纳入 baseline。
5. UML 图与代码的一致性由人工审查保证；代码与 UML 不一致时，先修 UML（或走变更流程），再改代码。

## 6. 人工审查要求

1. 所有 Agent 生成内容（规格、UML、设计、代码、测试）**必须经人工审查**后方可进入下一阶段或被采纳。
2. 人工审查重点包括：是否符合本宪法、是否满足业务规则、是否与既有 Spec 一致、是否有安全隐患。
3. 未经人工审查的 Agent 产物不得合并进主分支、不得作为交付物、不得作为后续实现依据。

## 7. 架构约束：分层架构与 MVC

1. 系统必须采用**分层架构**，至少包含以下层次，且依赖方向自上而下、不得逆向依赖：
   - 表示层（Presentation/API 层）
   - 业务层（Business/Service 层）
   - 数据访问层（Repository/DAO 层）
   - 实体/领域层（Entity/Domain 层）
2. 表示层采用 **MVC 模式**（后端为 FastAPI，前端视图与后端控制器职责清晰分离）。
3. 层次之间通过接口/抽象交互，禁止跨层直接访问（如 Controller 直接操作数据库、Service 直接返回 ORM 实体给视图等）。
4. 每层职责单一：表示层负责请求解析与响应，业务层负责业务逻辑与规则，数据访问层负责持久化，实体层负责领域概念。

## 8. 业务规则落位约束

1. **业务规则（借阅规则、罚款规则、预约规则、读者类型限额等）必须写在业务层（Service），严禁写入 Controller。**
2. Controller 只负责参数校验、调用 Service、组装响应，不得包含任何业务判断分支。
3. 涉及多种读者类型与借出物类型组合的限额、超期、罚款规则，应通过清晰的策略/规则对象或查询表实现，禁止散落在多个 Controller 中重复硬编码。
4. 数据库约束（唯一性、外键、非空）与业务规则应分层配置，避免业务规则仅依赖数据库触发器或仅依赖代码。

## 9. 权限控制约束

1. 系统必须实现基于角色的访问控制（RBAC），明确区分读者、学生读者、教师读者、图书管理员、系统管理员的权限边界。
2. 每个用例/接口必须声明其所需角色，后端在每个受保护接口上强制校验权限，不得仅依赖前端隐藏按钮。
3. 借阅证办理、图书/副本维护、管理员维护等敏感操作仅限对应管理员角色执行。
4. 权限校验逻辑应集中、可复用，禁止在多个 Controller 中重复实现校验逻辑。

## 10. 测试约束

1. **核心用例必须有自动化测试**：注册、办理借阅证、借阅、归还、查询借阅信息、预约、超期罚款计算、权限控制。
2. 测试应优先采用单元测试覆盖业务规则（借阅限额、罚款计算、预约分配顺序等），并辅以集成测试覆盖接口链路。
3. 权限相关的测试用例（越权访问被拒绝）为必测项。
4. 测试与 Spec 一一对应，每条核心业务规则至少有一条断言用例。
5. 提交代码前必须运行测试并通过；未通过测试的代码不得视为完成。

## 11. 禁止事项（红线）

1. 禁止在 Controller 中编写业务规则。
2. 禁止使用非文本格式的 UML 图作为规格。
3. 禁止擅自修改 baseline 后的 Spec 与设计文档。
4. 禁止跳过人工审查直接采纳 Agent 生成内容。
5. 禁止绕过权限控制或在前端做"假权限"。
6. 禁止核心用例缺少自动化测试。

## 12. 优先级与冲突解决

当各规范文件出现冲突时，按以下优先级裁决：

1. 本宪法（Constitution）
2. Specs（需求规格，baseline 后）
3. UML 设计文档
4. 代码实现与测试

低优先级内容与高优先级内容冲突时，须按高优先级修正低优先级内容；如须偏离高优先级，必须走人工批准的变更流程。
